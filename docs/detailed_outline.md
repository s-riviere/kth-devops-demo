# 🎯 Plan Demo Week6

## 🌟 Key Differentiating Points (vs Demos #2990 and #3090)

1. **"SBOM-First" Approach & Unix Decoupling (vs Trivy #3090)**:
   * Unlike Trivy’s all-in-one approach, we adhere to the Unix philosophy (*1 tool = 1 job*). **Syft** generates a vendor-neutral, standardized inventory (SPDX/CycloneDX), and **Grype** analyzes it. The SBOM can be archived, signed, or re-scanned cold without re-running the container.
2. **System + Application Detection Depth (vs Dependabot #2990)**:
   * Dependabot only inspects application source manifests (`requirements.txt`). Our toolchain inspects the compiled, real container image: operating system packages (`apk`/`apt`), the Python runtime, and application dependencies (`pip`).
3. **DevSecOps Maturity & Realism (*System Reasoning*)**:
   * Accounting for real-world constraints: handling unpatched upstream CVEs via `.grype.yaml` / `only-fixed`.

### 1. Introduction, Context and Problem (0:00 – 0:45 | ~45s)

* **Slide**: Slide 1 then 2.
* **Key Points**:
  * Present the small app containerized with Docker with an outdated OS.
  * App vulnerable to Software Supply Chain Attacks
  * Vulnerabilities hide in both application depandencies (`requirements.txt`) and Docker image OS (`Dockerfile`).
  * UNIX philosophy: 1 tool, 1 job
  * Clear separation of concerns: **Syft** generates the SBOM in standard SPDX-JSON format, while **Grype** performs the security analysis.

---

### 2. Syft and Grype prensentation and local test (0:45 – 2:00 | ~1 min 15s)

* **Key Points**:
  * Execution of Syft and Grype in local on the app docker image.
* **Execution**:
  1. Build local Docker image:
     ```bash
     docker build -t demo-app:local .
     ```
  2. Generate SBOM inventory with Syft:
     ```bash
     syft demo-app:local -o spdx-json > sbom.spdx.json
     ```
  3. Scan SBOM file with Grype (terminal output + SARIF export):
     ```bash
     grype sbom:sbom.spdx.json --only-fixed -o table -o sarif=results.sarif
     ```
* **Audience Observation**:
  * Fast, near-instantaneous SBOM generation.
  * Grype terminal table listing both system (`apk`/`dpkg`) and application (`python`/`pip`) packages side-by-side.
  * Usage of `--only-fixed` to ignore vulnerabilities with no fix available. This is ok for our non critical application.
  * Results of Grype are visible in the terminal with different vulnerabilities with different level of importance.
  * Creation of a reusable `results.sarif` report file ready for security platform ingestion or as a log.

---

### 3. Remote solution: CI/CD Quality Gate (2:00 – 3:00 | ~1 min 00s)

* **Key Points**:
  * We can transferm these local tools for automated security enforcement of projects using a GitHub Actions *Quality Gate*.
  * Pipeline is defined in `security-gates.yaml`: 
    * *Zero Trust Build* meaning that the pipeline doesn't rely on existing files, it does all the process from the Docker image building.
    * Use of the `only-fixed` flag to ignore vulnerabilities that have not been corrected yet.
    * Severity cutoff set to *Critical* to refuse pull requests with critical vulnerabilities.
    * The *SBOM* (artifact of Syft) and *.sarif* (artifact of Grype) are generated by the CI and saved on Github Actions, and they can be used as logs or to make a dashboard of vulnerabilities.
* **Execution**:
  * Open browser to the pre-created GitHub Pull Request based on `python:3.9-slim-buster` to see that it failed

---

### 4. Live Change & Build-Time Commentary (3:00 – 5:00 | ~2 min 00s)

* **Key Points**:
   * Try a new OS for the Docker image.
* **Execution**:
  1. Edit line 1 of `Dockerfile`: replace `FROM python:3.9-slim-buster` with `FROM python:3.12-alpine`.
  2. Commit and push changes to the PR branch:
     ```bash
     git commit -am "fix: switch base image to alpine for security gate" && git push
     ```
  3. Commentate live during pipeline execution (~1 mn 40s):
     * `python:3.9-slim-buster` was an outdated OS no longer maintained which was too powerful and heavy for our little app.
     * Alpine is smaller and has a reduced attack surface (removal of `bash`, `curl`, and non-essential OS utilities).
     * The Github CI pipeline does all the process by itself (from image build to grype evaluation) because of no trust policy.
* **Audience Observation**:
  * Live code modification triggering an automated CI re-run.
  * After 1mn30s, the GitHub Actions job turns **GREEN** and we can merge.

### 5. Critical Reflection (*System Reasoning*) (5:00 – 7:00 | ~1 min 30)

* **Slides**: Slide 3
* **Key Points**:
  * Slide content.
  * System overhead: About 2mn for each PRs to prevent part of Supply Chain Attacks.
  * Vulnerability DB Freshness: Scanner accuracy relies on recent DB updates so it contains the most recent CVEs. It can be parametrized with `.grype.yaml`.
  * Unpatched Upstream CVEs: Handling unfixable upstream vulnerabilities gracefully via `only-fixed: true` or documented `.grype.yaml` exceptions.
  * Defense-in-Depth / Conclusion: Image scanning is good but must be paired with non-root runtime users and read-only filesystems.
